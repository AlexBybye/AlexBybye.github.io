# DTS-SQL-2A42: Decoupled Text-to-SQL with Four-Stage Cascade Pipeline (Updated)

  

## 项目概述

  

DTS-SQL-2A42 是一个基于 **DTS-SQL（Decoupled Text-to-SQL）** 范式的 Text-to-SQL 系统，底座模型统一使用 **Qwen2.5-Coder-7B-Instruct**。整体采用 **4 阶段级联流水线**（4-Stage Cascade Pipeline），将端到端的 SQL 生成任务分解为四个渐进式子任务。

  

**与原版 DTS-SQL 的核心区别**：本系统在每个阶段都引入了针对级联误差传导的防御机制——Stage2 的 Uncertainty-Aware Schema Expansion 补偿 Stage1 漏表、Stage3 的 KBE-Aware 多策略生成 + Intent-Signal Selector 补偿 Stage2 sketch 错误、Stage4 的 Pool-Consensus-Protected Repair 避免过度修复。

  

```

自然语言问题 (Question)

        │

        ▼

┌───────────────────────────────┐

│  Stage 1: Schema & Value     │  [六轨制 Grounding + M-Schema + Backward SQL]

│  Grounding                    │  输出: schema_subgraph + value_bindings

└───────────────────┬───────────┘

                    │

                    ▼

┌───────────────────────────────┐

│  Stage 2: Query Sketch       │  [Schema Expansion + Multi-Sketch + Consistency Verify]

│  Generation                  │  输出: SQL Sketch (结构化骨架)

└───────────────────┬───────────┘

                    │

                    ▼

┌───────────────────────────────┐

│  Stage 3: SQL Fill           │  [KBE-Aware SFT + Multi-Prompt + Adaptive Scoring

│  Generation                  │   + Intent-Signal Override]

│                               │  输出: 完整可执行 SQL

└───────────────────┬───────────┘

                    │

                    ▼

┌───────────────────────────────┐

│  Stage 4: Error-Type-Aware   │  [KBE-Injected Repair + Pool Consensus Protection

│  Refinement                  │   + Multi-Temperature Voting]

└───────────────────────────────┘

```

## Stage 1: Schema & Value Grounding

  

### 1.1 任务定义

  

给定自然语言问题，从整个数据库 schema 中识别出解决问题所需的相关表、相关列，以及 WHERE 条件中的值绑定（value bindings），并输出一个结构化的 **schema subgraph**。

  

具体输出：

  

- `relevant_tables`: 相关表列表

- `relevant_columns`: 相关列列表（每列包含所属表、列名、原因）

- `value_bindings`: 值绑定列表（每个绑定包含原文中抽取的值、值的类型、目标列、操作符）

- `schema_subgraph`: 包含相关表节点列表和 FK 边列表的子图结构

  

### 1.2 技术方案：newidea511

  

#### 1.2.1 M-Schema（增强型 Schema 表示）

  

**核心思想：** 传统的 schema 表示（如只列出表名和列名）无法帮助模型区分语义相似的列。例如，`concert.Year`（演出年份）和 `stadium.Capacity`（场馆容量）在列名层面毫无线索，但它们各自的样本值（`"2014"`, `"2015"` vs. `"5000"`, `"8000"`）可以立即区分。

  

**M-Schema 格式：**

  

```

【DB_ID】 concert_singer

  

【Schema】

  

# Table: singer

[

  (Singer_ID:INTEGER, Primary Key),

  (Name:TEXT, Examples:["Adele","BTS"]),

  (Country:TEXT, Examples:["UK","Korea"]),

  (Age:INTEGER, Examples:["28","35"])

]

  

【Foreign keys】

concert.Stadium_ID = stadium.Stadium_ID

concert.Singer_ID = singer.Singer_ID

```

  

每列附带的 **Examples** 从 SQLite 数据库中实时采样（每列取 3 个不重复的非空值），用于消除列之间的歧义。

  

**SchemaValueCache** 机制：为每个 `db_id` 在内存中缓存样本值，避免重复打开 SQLite 文件。所有样本值都经过数值检测过滤——若一列的值全是可解析为浮点数的内容（如 ID 列），则不展示到 prompt 中，以节省 token。

  

#### 1.2.2 六轨制 Grounding（Six-Track Grounding）

  

六轨制 Grounding 是将伪 schema（pseudo-schema，由 Stage 1 zero-shot 生成）映射到真实数据库 schema 元素的核心模块。六轨分别对应六种互补的匹配策略：

  

**Track 1 — 语义匹配（Semantic Track）：**

使用 sentence-transformer 模型（`all-MiniLM-L6-v2`）对 pseudo 名称和 real 名称分别编码，计算 cosine similarity，取 top-K（默认 K=3），阈值 0.3。语义编码能够捕捉同义词和上位词关系。

  

**Track 2 — 字面匹配（Literal Track）：**

使用两种字面相似度：token 重叠度（Jaccard，按 underscore/space 分词，阈值 0.45）和子串匹配（case-insensitive，去除下划线，任意方向包含即可）。该轨道精度高，捕获 embedder 可能遗漏的精确词汇匹配。

  

**Track 3 — Fallback 兜底（Fallback Track）：**

`force_top1=True` 确保每个 pseudo 元素至少匹配到一个 real 元素——保证没有 null grounding，避免漏召。

  

**Track 4 — 证据匹配（Evidence Track）：**

从 SQLite 数据库中采样每列的值（每列最多 5 个不重复值）。将问题 token 集合（去停用词后）与样本值集合做交集，若交集非空，则将该 `table.column` 纳入候选。该轨道对于基于具体数值的问题（如 "2014年以后的演唱会"）尤为重要。

  

**Track 5 — 结构键注入（Structural Track）：**

将每个候选表的 Primary Key 和 Foreign Key 列强制加入候选集，确保 JOIN 所需的键列不会被遗漏。

  

**Track 6 — 连接路径注入（Connection Track）：**

使用 `networkx` 构建 FK 图（节点=所有表，边=FK 关系）。对每一对候选表，计算最短 FK 路径，并将路径中的中间表加入候选集。**关键约束**：中间表只有在其表名或列名包含问题 token 时才被加入，避免过度膨胀候选集。

  

六轨的结果经过置信度分级标注：

  

- `Confirmed`：综合得分 > 0.8

- `High_Potential`：综合得分 > 0.4

- `Candidate`：其余

  

#### 1.2.3 Backward SQL 候选集

  

**核心思想：** 传统的 forward 方式直接让模型列出相关表和列，而 backward 方式让模型先生成一段 draft SQL，再从 draft SQL 中解析出 `table.column` 引用。两种方式的错误模式不同（语义理解错误 vs. SQL 生成习惯），取并集可以提升召回率。

  

**Backward Pipeline：**

  

1. **Backward Pass**：加载 backward adapter，基于 M-Schema prompt 让模型生成一段 draft SQL（纯 SQL，不要求输出 JSON schema）。

2. **SQL 解析**：使用正则表达式从 draft SQL 中提取 `table.column` 引用（FROM/JOIN 中的表名、别名解析后的qualified 列名），仅保留属于真实 schema 的元素，丢弃幻觉名称。

3. **结果合并**：`merge_forward_backward(forward_result, backward_result)` — 取 union，forward 的置信度在冲突时优先。

  

#### 1.2.4 Forward + Backward 双 Adapter 训练

  

Stage 1 训练两个独立的 LoRA adapter：

  

| Adapter          | 训练目标                              | Epochs | Learning Rate | 输出格式                                              |

| ---------------- | ------------------------------------- | ------ | ------------- | ----------------------------------------------------- |

| Forward Adapter  | M-Schema prompt → JSON schema linking | 3      | 2e-4          | `relevant_tables + relevant_columns + value_bindings` |

| Backward Adapter | M-Schema prompt → draft SQL           | 2      | 2e-4          | SQL 片段（用于提取候选列）                            |

  

**训练策略：**

  

- **标签 Mask**：仅对输出 JSON 区域（` ```json … ``` ` fence 内部）计算 loss，prompt 部分 token 全部标记为 `-100`，使模型只学习生成答案而非重复 prompt。

- **序列截断策略**：总长度超过 3072 token 时，进行**右对齐截断**（drop 前缀），保证输出 JSON 区域完整。

- **断点恢复**：训练脚本自动检测 `checkpoint-*` 目录，若 final checkpoint 因保存崩溃而缺失，自动回退到最新的 checkpoint。

  

**LoRA 配置：** `r=16, lora_alpha=32, lora_dropout=0.05`，更新所有 Linear 层（q/k/v/o + gate/up/down）。

  

### 1.3 Stage 1 推理流程

  

```

Step 1 — Pseudo-Schema 生成（zero-shot，无 adapter）

    LLM base model (无 schema 访问) → hallucinated table/column names

  

Step 2 — 六轨制 Grounding

    pseudo schema + 真实 schema → real table/column candidates (六轨)

  

Step 3 — Forward + Backward 双通道推理

    Forward adapter: M-Schema + candidates → JSON schema linking

    Backward adapter: M-Schema + candidates → draft SQL → backward candidates

    → 合并结果

  

Step 4 — 评估（Subgraph Accuracy）

```

## Stage 2: Query Sketch Generation（新方案）

  

### 技术方案：newway

  

相比原 newidea57（单路径生成，GT 输入整体正确率 91.59%），newway 引入三个核心模块，将 Stage2 从"单 sketch 生成器"升级为"容错 sketch planner"：

  

#### 2.1 Uncertainty-Aware Schema Expansion（Module A）

  

**动机**：Stage1 的 Subgraph Accuracy 93.62%，意味着 ~6.4% 的题 Stage1 漏选了关键表。一旦漏表，Stage2 无法生成正确的 JOIN 路径。实测 Tables 精确匹配从 GT 输入的 99.23% 掉到级联输入的 93.71%（-5.52 pp），是级联误差传导的最大来源。

  

**方法**：在 Stage1 和 Stage2 之间插入 schema 扩展层：

  

```

Stage1 output (relevant_tables + FK graph + full_schema)

    ↓

Schema Expansion:

  core_tables     = Stage1 高置信表

  bridge_tables   = FK 图 Steiner tree 中间表（连接 core tables 所需）

  answer_tables   = 从问题文本推断的 SELECT 目标表

                    （如 "id of students" → student 表，即使 Stage1 未召回）

  optional_tables = core 表的 1-hop FK 邻居（备用）

    ↓

expanded_schema_candidates → 输入 Stage2

```

  

**关键设计**：

- **answer_tables 推断**：从问题中提取 SELECT 目标实体（如 "name of the makers"），在 full_schema 中查找匹配表名，若该表与 core_tables 有 FK 连接则补入

- **bridge_tables 计算**：用 networkx 在 FK 图上对 core_tables 做 Steiner tree 近似，找到连接所有 core tables 所需的最少中间表

- **不盲目扩张**：optional_tables 只作为 prompt 中的"备选"展示，不强制使用

  

#### 2.2 Multi-Sketch Generation + Consistency Verification（Module B + C）

  

**动机**：单路径生成的 sketch 一旦选错表或漏掉 JOIN，后续 Stage3 无法补救。多路径生成 + 确定性验证可以对冲单路径风险。

  

**Multi-Sketch Generation（3 种 schema 视角）**：

  

| 视角 | Schema 范围 | 目的 | 对应错误类型 |

|------|------------|------|------------|

| Conservative | 只用 Stage1 原始表 | 避免多余表 | 修 EXTRA_TABLE |

| Expanded | core + bridge + answer tables | 避免漏表 | 修 MISSING_TABLE |

| Value-driven | value_bindings 引用的表 + FK 邻居 | 以值为中心 | 修 WHERE 错误 |

  

**Prompt 改进（vs newidea57）**：

- 新增 `## Foreign Key Join Paths` 段落，显式给出 FK 连接关系

- 新增 `## Column Constraint` 提醒模型只能用 schema 中存在的列

- 保留列消歧 description 和样本值标记

- 保留表角色注释（table role）

  

**Sketch Consistency Verifier（确定性规则打分）**：

  

对每个候选 sketch 做 7 项结构检查，打分排序选最优：

  

| 检查项 | 说明 |

|--------|------|

| Column validity | 引用的列是否存在于 used tables 中 |

| Table connectivity | 所有 used tables 是否在 FK 图中连通 |

| Join path coverage | join_path 是否覆盖所有表 |

| Value binding coverage | value_bindings 是否反映在 WHERE 中 |

| Aggregation/GROUP BY 兼容性 | 有聚合函数时是否有 GROUP BY |

| Superlative 模式检查 | 是否有 ORDER BY + LIMIT |

| EXCEPT/INTERSECT 一致性 | 否定词是否与集合操作匹配 |

  

3 个候选按 score 排序，选最高分的输出。

  

#### 2.3 训练策略

  

- 基于 newidea57 adapter **继续训练**（不从头训），继承已有的 sketch 生成能力

- 训练时用 **expanded schema**（让模型学会处理 bridge tables）

- **15% 样本做 sketch corruption**（删表/加表/换算子/删 LIMIT/换聚合函数/打乱 SELECT 顺序），target 仍是正确 sketch → 模型学会从 noisy input 恢复

- 保留多 WHERE 条件上采样（×2）

  

#### 2.4 推理流程

  

```

Stage1 output

    ↓

[1] Schema Expansion → expanded_schema_candidates

    ↓

[2] 3 种视角各生成 1 个 sketch 候选

    ↓

[3] Sketch Consistency Verifier 打分排序

    ↓

[4] 输出最优 sketch

```

## Stage 3: SQL Fill Generation（新方案）

  

### 技术方案：newway520-all-new-copy-improve

  

Stage3 是整个流水线中改动最大的阶段。核心思路：**KBE-Aware 训练 + 多策略推理 + 9 步自适应打分流水线 + Intent-Signal Override**。

  

#### 3.1 KBE-Aware SFT 训练（KBE 信号下沉到 weight）

  

**动机**：在推理 prompt 中注入 KBE 语义知识，模型"看见"但不一定"信"。将 KBE 下沉到训练阶段，让模型权重内化"看到 KBE 就该这么写"的偏置。

  

**方法**：在已有 SFT adapter 之上继续训练 2 epoch：

- 输入：GT sketch + KBE 注入 prompt

- 输出：SQL

- 训练数据：Spider train + Stage3 train data

- 保存为 `KBE-SFT/final` checkpoint

  

```

训练 prompt 结构:

  ## Database Semantics (CRITICAL):

  {kbe_hint for this db_id}

  

  ## Question: {question}

  ## Schema: {M-Schema with samples}

  ## Sketch: {GT sketch}

  ## Output:

  ```sql

  {label_sql}

```

```

  

#### 3.2 DB Semantics Knowledge Base Entry (KBE)

  

为 18 个高错库构建结构化语义知识库（`db_semantics_kbe.json`）：

  

| 字段 | 说明 | 示例 |

|------|------|------|

| `db_context` | 库的领域描述 | "汽车制造商数据库（4 表）" |

| `high_risk_columns` | 最常被误用的列 | `car_makers.maker`: "制造商标识码，不是品牌全称" |

| `join_paths` | 推荐 FK 连接路径 | `maker_to_car: CAR_MAKERS.Id = MODEL_LIST.Maker → ...` |

| `disambiguation_rules` | 三段式硬触发规则 | trigger → guidance → applies_to_questions |

  

KBE 贯穿 Stage3 训练（3.1）、Stage3 推理（3.3 Step 1/7）、Stage4 修复（4.2）三个环节。

  

#### 3.3 推理流水线（9 步）

  

```

[训练] 沿用 KBE-Aware SFT adapter（不重训）

        ↓

[推理] Stage2 sketch + Stage1 output

    ↓

[Step 1] 加载 db_semantics_kbe.json（18 库，含 28 条硬触发 rules）

    ↓

[Step 2] 构建 3 套 Prompt + KBE 注入

         - vanilla:        sketch-driven 基线

         - set_logic:      强调 NOT IN/EXCEPT/INTERSECT/HAVING

         - column_synonym: 注入列描述 + value evidence 消歧

    ↓

[Step 3] 多温度采样（vanilla 0.8 / set_logic 1.0 / column_synonym 0.9）

         每 prompt 8-9 条，原始上限 ~25 候选/题

    ↓

[Step 4] 去重 + DB-Aware Post-Correction

         - WHERE 值空格修复

         - 列名大小写修复

         - 列幻觉检测

    ↓

[Step 5] 严格列白名单过滤

         - strict: col_score = 1.0 才通过

         - relaxed fallback: col_score >= 0.5（避免全砍）

    ↓

[Step 6] Sketch Constraint Scoring（加法 bonus，权重 0.10）

         - sketch 从乘法因子改为加法 bonus

         - 避免 Stage2 错传导锁死天花板

    ↓

[Step 7] KBE Semantic Validation + DB Validation

         - KBE 规则校验（违反者扣分/拒绝）

         - 执行验证（非空=1.0 / 空=0.3 / 崩=0.0）

    ↓

[Step 8] Pairwise Selector + Verifier + Source-aware Rank

         - PairwiseSQLSelector: 候选间两两比较

         - Stage3Verifier: 执行结果 + 结构验证

         - Source-aware Rank: 每个 source 内部独立排序

    ↓

[Step 9] Adaptive Combined Scoring + Intent-Signal Override

```

  

#### 3.4 自适应打分公式

  

**多候选（≥3 个有效执行结果）**：

​```python

base = (

    0.30 * consistency      # 执行结果多数簇一致性

  + 0.20 * db_validation    # 执行非空验证

  + 0.15 * selector         # PairwiseSelector 分数

  + 0.10 * verifier         # Stage3Verifier reward

  + 0.15 * col_gate         # 列白名单分数

  + 0.10 * source_rank      # source 内部排名

)

score = col_gate * base

      + 0.10 * sketch_bonus   # sketch 一致性（加法，非乘法）

      + intent_bonus           # set-logic intent (+0.25 for INTERSECT/HAVING)

      + kbe_adjustment         # KBE 规则加减分

```

  

**少候选（≤2）**：

```python

base = (

    0.30 * db_validation + 0.20 * selector + 0.20 * verifier

  + 0.15 * col_gate + 0.15 * source_rank

)

score = col_gate * base + 0.10 * sketch_bonus + intent_bonus + kbe_adjustment

```

  

#### 3.5 Intent-Signal Override（A1）

  

在 Step 9 最终选择之后，加入关键词意图信号的 override 机制：

  

**信号表**：

  

| Q 关键词模式 | SQL 特征 | 权重 |

|-------------|---------|-----:|

| both X and Y / above N and below M | INTERSECT | +0.08~0.10 |

| either X or Y | UNION/INTERSECT | +0.06 |

| different/distinct/unique/various | DISTINCT | +0.06 |

| neither X nor Y | EXCEPT/NOT IN | +0.07 |

| not/never/no | EXCEPT/NOT IN | +0.03 |

| each/per/for every + aggregate | GROUP BY | +0.04 |

| list X and Y | SELECT ≥ 2 列 | +0.03 |

| how many/count of | aggregate | +0.03 |

  

**Override 逻辑**：

```

if A1_best_candidate ≠ selector_choice

   AND A1_score_gap > 0.03

   AND A1_best_candidate 执行成功且非空:

     → override selector 选择

```

  

**设计原理**：A1 的 +0.06~0.10 在 base score ~0.5-1.0 的量级下太小，无法通过直接加分翻盘（因为 consistency vote 的 0.225 差距远大于 A1 的 0.08）。Override 机制绕过 consistency 的压制，在"A1 有强信号且候选可执行"时直接覆盖。

  

**实测**：在 newway520 候选池上 +2 条 / 0 regression（EX strict 0.8414 → 0.8433）。

  

#### 3.6 关键设计决策

  

| 决策 | 原因 |

|------|------|

| sketch 从乘法→加法 | Stage2 自身 14% 错率，hard sketch 锁死天花板 |

| Source-aware rank | vanilla 候选数偏多（6 vs 5+5），消除数量优势 |

| KBE 补 28 条硬触发 rules | 5 个高错库（dog_kennels/student_transcripts/wta_1/flight_2/cre_Doc）累计 -9 错 |

| A1 用 override 而非直接加分 | 直接加分被 consistency vote 压制，override 才能翻盘 |

| 不用 majority-cluster bonus | 实测双重计数有害（抵消 A1 增益） |

## Stage 4: Error-Type-Aware Refinement（新方案）

  

### 技术方案：newidea-final

  

Stage4 从"执行失败修复器"升级为"带保护的智能修复器"，核心设计：

  

#### 4.1 三层触发决策

  

```

对每道题：

  1. 执行 Stage3 选中的 SQL

  2. 执行成功且非空 → 不修（保护 Stage3 selector 成果）

  3. 执行失败 → Phase A 修复

  4. 返回空 → 检查 Pool 共识：

     - ≥50% 候选也空 → 跳过（空是正确答案）

     - <50% 候选空 → Phase B 修复

```

  

**保护规则的必要性**：实验证明，对"执行成功且非空"的 SQL 做修复会引入 degradation（如把正确的 INTERSECT 改成错误的 UNION）。保护规则确保 Stage3 的 selector 成果不被破坏。

  

**Pool 共识检查的必要性**：Spider 中存在 GT 本身返回空的题目（如 "districts with stores < 3000 AND > 10000"，INTERSECT 后为空集）。若不检查 pool 共识，Stage4 会把正确的空结果"修"成错误的非空结果。

  

#### 4.2 KBE-Injected Repair

  

修复 prompt 中注入目标库的 KBE 语义知识：

  

```

### Database Semantics (READ BEFORE REPAIRING)

High-risk columns:

  - treatments.cost_of_treatment: 实际治疗费用，不是 Charges.charge_amount

Canonical join paths:

  - owner_to_treatment: Owners.owner_id = Dogs.owner_id → Dogs.dog_id = Treatments.dog_id

```

  

使 LLM 修复时不再幻觉列名/JOIN 路径。

  

#### 4.3 Multi-Temperature Voting

  

每轮修复生成 K=3 个候选（温度 0.3/0.7/1.0），加上 Stage3 pool 中的非空候选，投票选最佳：

  

```

score = 0.50 * (executable + non_empty)

      + 0.20 * (consensus_with_stage3_pool)

      - 0.10 * (same_as_original)

```

  

Stage3 pool 候选参与投票的关键意义：即使 LLM 修不出好的，pool 里原本就有的非空候选可以被选中——相当于给了 Stage4 一次"从 pool 里重新选"的机会。

## 各阶段方法汇总

  

| 阶段 | 核心方法 | 关键创新点 |

|------|---------|-----------|

| Stage 1 | 六轨制 Grounding + M-Schema + Backward SQL | Forward/Backward 双通道取并集提升召回 |

| Stage 2 | Schema Expansion + Multi-Sketch + Consistency Verify | Uncertainty-Aware 补偿 Stage1 漏表 + 多视角生成 + 确定性验证排序 |

| Stage 3 | KBE-Aware SFT + Multi-Prompt + Adaptive Scoring + Intent Override | KBE 下沉训练 + sketch 软约束 + A1 关键词 override |

| Stage 4 | KBE-Injected Repair + Pool Consensus Protection + Multi-Temp Voting | 保护规则防 degradation + pool 共识防过修 + KBE 提升修复质量 |

## 设计原则

  

1. **级联误差防御**：每阶段都有针对上游错误传导的补偿机制（Schema Expansion / sketch 软约束 / pool consensus）

2. **知识注入**：KBE 语义知识库贯穿 Stage3 训练、Stage3 推理、Stage4 修复三个环节

3. **保守修复**：Stage4 只修"明确有问题"的 SQL，执行成功非空的不动（0 degradation 优先于 +N improvement）

4. **候选多样性**：Stage3 多策略生成 + Stage4 pool 候选参与投票，最大化正确 SQL 出现在候选池中的概率

5. **信号互补**：8 个打分信号（consistency / db_val / selector / verifier / col_gate / src_rank / sketch / kbe_adj）+ A1 intent override，覆盖不同维度的正确性判断
