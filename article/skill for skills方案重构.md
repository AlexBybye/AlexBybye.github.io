## 一、批评意见的事实核查

这份批评分析对当前系统设计的大部分判断是**准确的**，但也存在部分夸大和一处事实错误。

### 1.1 符合事实的判断（✅）

**架构过度重型化（✅）** ：系统确实包含5大宏观阶段、30+内部状态、6类以上JSON数据契约。这种复杂度对于一个以生成和优化Markdown提示词为核心的Skill系统而言，确实存在“用火箭控制系统管理提示词”的嫌疑。

**评测成本结构畸形（✅）** ：批评指出的“轻量Q1模式无法轻量化”切中要害。当前设计Q1仍需走完整状态机前置节点，固定开销远大于用例变动成本——这确实是分层设计中的典型“固定成本陷阱”。

**宿主API依赖脆弱（✅）** ：不同宿主对Skill的定义、能力边界、运行逻辑确实不统一。系统试图抽象通用语义，最终确有可能沦为“最小公分母适配”。批评指出的“跨宿主场景高级特性全部被迫降级”是现实的工程风险。

**评测集过拟合（✅）** ：这是Agent评测领域的公认难题。现有研究表明，只看验证曲线很容易高估泛化能力；离线刷榜分数与线上用户体验的相关性已降至0.3以下。当前系统确实缺少对用例质量和领域覆盖度的标注机制。

**LLM评审循环缺陷（✅）** ：LLM-as-Judge确实存在系统性不一致问题。批评指出的“归因误判→错误修改→证据固化”的循环偏差，是LLM驱动自进化系统的经典风险。

### 1.2 部分夸大或不准确（⚠️）

**“投入产出比极低”缺乏证据（⚠️）** ：批评断言“最终产出的Skill效果仅比人工手写提升极少幅度”，但SkillsBench的实际数据显示：**人工策划的Skills平均提升16.2个百分点**。对于特定领域（如医疗健康）提升可达51.9个百分点。真正的问题是“模型自生成的Skills不仅无用甚至有害”——这恰恰说明优化器本身的价值在于**人工策划与自动生成的边界控制**，而非优化器没有价值。

**“元Agent自我吞噬”存在偷换概念（⚠️）** ：批评将“优化器的复杂度可能超过被优化Skill的复杂度”作为根本缺陷。但这实际上是**所有元系统**的共性——编译器比它编译的代码复杂，测试框架比被测试的应用复杂。这本身不是缺陷，除非复杂度与收益不成正比。当前设计的问题在于复杂度是**刚性的**（所有模式都要承受全部开销），而非元系统本身不该存在。

### 1.3 一处事实错误（❌）

**“系统未设置任何规则校验评测器本身的偏差”（❌）** ：这与规格文档的事实不符。`WORKFLOW_SPEC.md` 第10.2节明确规定：“评测引擎检测恒过、恒败、低区分度和高错误率 criteria，并阻止无效门禁进入发布裁决”。第11.6节要求 `assessments.jsonl` 记录 evaluator 类型、版本、是否盲化，且 decision validator 会拒绝 evaluator 版本漂移的 assessment。系统确实设计了校验机制，只是这些机制在批评中被忽略了。


## 二、重构修改方案

基于上述事实核查，当前系统的核心矛盾是：**刚性的重型架构无法弹性适配不同复杂度的任务**。重构应围绕“弹性缩放”展开。

### 2.1 核心架构调整：从“状态机驱动”到“策略驱动”

当前设计的问题在于状态机是**硬编码的**——无论Q1还是Q3，都要经过相同状态节点。重构方案：

**将流程退化逻辑提升为配置数据**（与批评意见一致）：

```text
workflow-profiles/
  q1-light.yaml      # 结构校验 + 2核心用例 → 直接输出
  q2-standard.yaml   # 状态机全流程（默认配置）
  q3-deep.yaml       # 状态机全流程 + 高级模块
  custom-*.yaml      # 用户自定义
```

每个profile声明：
- 必须执行的状态节点（不可跳过）
- 可跳过的状态节点及跳过条件
- 每个节点的超时和重试策略
- 输出claim_cap（声明上限）

**状态机本身改为profile interpreter**：状态节点不再是硬编码路径，而是由profile决定执行哪些节点、跳过哪些节点、何时提前终止。Q1的“轻量”体现在**节点数量少**而非“流程简化但节点全走”。

### 2.2 Q1真正轻量化：早切割、快收尾

当前Q1的问题在于仍然要经过 `GOAL_CARD_DRAFT → READ_ONLY_DISCOVERY → ROUTE_PROPOSAL → ...` 的完整前奏。重构后Q1的profile：

```text
q1-light:
  entry: INTAKE
  nodes:
    - GOAL_CARD_DRAFT (简化版：只提取目标和硬约束)
    - STRUCTURE_CHECK (必须)
    - CORE_EXECUTION (2个核心用例)
  exit: 任一核心用例通过 → 输出候选Skill
        两个都失败 → 输出失败报告，不迭代
  skip: 独立方案、逐项裁决、路由评测、留出集、盲评
  claim_cap: "仅通过2个核心用例的结构和功能验证，未测试路由、泛化或边界"
```

这样Q1的固定开销被压缩到**可接受的最小集合**，且声明上限清晰透明。

### 2.3 适配层重构：从“通用抽象”到“能力协商”

当前适配器被动声明能力，核心被动处理降级。重构方向：

**双向能力协商**：

```text
核心 → 适配器：我需要这些能力 [isolated_runs, token_metrics, auto_route_eval]
适配器 → 核心：我能提供 [isolated_runs: true, token_metrics: false, auto_route_eval: degraded]
核心 → 适配器：基于你的能力，我启用以下模块...
```

这样核心可以根据适配器的实际能力**动态裁剪评测计划**，而不是在“全功能”和“全部降级”之间二选一。对于不支持的能力，核心自动调整 `claim_cap` 而非阻塞或假装支持。

### 2.4 评测泛化能力增强

针对评测集过拟合问题，引入**动态任务生成**机制（参考SEAGym的思路）：

- 使用 **Scenario Model** 每轮生成样本外任务
- baseline 和 candidate 在同一批新任务上做配对比较
- 用例质量标注为独立字段：领域覆盖度、难度等级、真实来源标记
- 质量权重影响最终裁决，高质量用例权重高于低质量用例

### 2.5 LLM评审的制衡机制

针对LLM-as-Judge的循环缺陷，增加制衡层：

- **双模型交叉验证**：主要评审和复核评审使用不同模型（或同一模型的不同配置）
- **确定性检查优先**：能用确定性验证器就不用LLM评审（SkillsBench的做法正是如此）
- **评审结果置信度阈值**：低置信度结果触发人工介入，而非自动采纳
- **评审偏差追踪**：记录每个评审模型的历史偏差模式，用于校准后续评审


## 三、可借鉴的相关论文

### 3.1 SkillsBench（2026）—— 最直接相关

**核心贡献**：首个系统性评估Agent Skills的基准测试，覆盖11个领域86个任务，7种模型配置，7,308条推理轨迹。

**可复用逻辑**：
- **三条件评测范式**：无Skill / 人工策划Skill / 自生成Skill，实现效用的可归因测量
- **确定性验证器优先**：避免LLM-as-Judge的方差问题
- **关键发现**：模型自生成的Skills整体无提升；聚焦式2-3模块Skill优于长文档

**对当前系统的启示**：优化器的核心价值不应是“让模型自己写Skill”，而应是 **“判断何时该由人工策划、何时可自动生成、何时不创建”** 。这与当前规格中 `NO_SKILL_CONFIRMED` 的设计方向一致。

### 3.2 SkillGenBench（2026）

**核心贡献**：评估Skill生成流程的基准，区分“任务已知后生成特定Skill”和“任务未知前蒸馏可复用Skill库”两种模式。

**可复用逻辑**：
- **两种生成模式**的区分——当前系统对所有任务采用相同的创建流程，实际上任务特定Skill和通用Skill库的生成策略应该不同
- **多源输入处理**：从代码仓库 vs 长文档提取procedural knowledge的失败模式不同——当前系统对所有来源一视同仁

### 3.3 Agent Skill Evaluation and Evolution Survey（2026）

**核心贡献**：系统性综述Skill进化与评估的四个范式——执行反馈、轨迹蒸馏、压缩、强化学习。

**可复用逻辑**：
- **进化范式的分类框架**：当前系统的优化路径本质上是“执行反馈”范式，但未充分利用轨迹蒸馏和压缩
- **Skill-centric benchmark的六大类别及其结构性缺口**——可作为当前系统评测设计的外部参考

### 3.4 AgentSkillOS（2026）

**核心贡献**：Skill生态系统的组织、编排与管理框架，包含能力树检索和DAG流水线。

**可复用逻辑**：
- **能力树组织**：将Skill组织成能力树进行高效发现——当前系统的“查重”机制过于简单
- **DAG编排**：结构化组合优于平铺调用——当前系统假设Skill是独立调用的

### 3.5 A Framework for Evaluating Agentic Skills at Scale（2026）

**核心贡献**：让Skill作者构建真实任务来评估Skill，对500个真实Skill生成1,000个衍生任务。

**可复用逻辑**：
- **从Skill内容生成评测任务**的方法论——当前系统的用例完全依赖用户提供，缺少从Skill自身推导测试用例的能力
- **指令遵循与目标完成的评分rubric**——可作为执行平面评测的参考

### 3.6 Evaluation and Benchmarking of LLM Agents Survey

**核心贡献**：LLM Agent评测的二维分类法——评测目标（行为、能力、可靠性、安全性）× 评测过程（交互模式、数据集、基准）。

**可复用逻辑**：
- **评测目标分类**：帮助当前系统明确每个评测维度的定位
- **评测过程框架**：可作为当前系统验证顺序的理论依据


## 四、总结

| 批评点 | 事实判断 | 重构方向 |
|---|---|---|
| 架构过度重型 | ✅ 符合事实 | 流程退化逻辑→配置数据，状态机→profile解释器 |
| 评测成本畸形 | ✅ 符合事实 | Q1早切割快收尾，固定开销最小化 |
| 宿主依赖脆弱 | ✅ 符合事实 | 双向能力协商，动态裁剪评测计划 |
| 评测集过拟合 | ✅ 符合事实 | 动态任务生成 + 用例质量权重 |
| LLM评审循环缺陷 | ✅ 符合事实 | 双模型交叉验证 + 置信度阈值 |
| 投入产出比低 | ⚠️ 部分夸大 | 人工Skill提升16.2%有实证，问题在自动生成边界 |
| 元Agent自我吞噬 | ⚠️ 偷换概念 | 元系统复杂度本身不是缺陷，刚性复杂度才是 |
| 无评测器校验 | ❌ 事实错误 | 规格已有校验机制，需加强执行 |

**最关键的认知修正**：当前系统的价值不在于“让模型自动写出好Skill”——SkillsBench已经证明这条路走不通。真正的价值在于**判断何时该创建、何时该优化、何时该停止**，以及对已有Skill进行**可验证的、有基线的、有回退的增量改进**。当前规格中的 `NO_SKILL_CONFIRMED`、不可变基线、compare-and-swap等设计方向是正确的，但被刚性的重型架构掩盖了。重构的核心任务就是**让这些正确设计能以弹性成本被执行**。
